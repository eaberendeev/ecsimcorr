# Анализ критической секции `apply_to_particles` (OpenMP)

Дата: 2025-09 (ветка `fix-dumping-fields`, код `second_emission`).
Анализ: orchestrator + @oracle (независимое второе мнение). Только анализ, без реализации.

---

## 1. Откуда взялась критическая секция

`#pragma omp critical` в `BoundaryConditionHandler::apply_to_particles`
(`srcBeren/utils/boundary_conditions/boundary_condition_handler.cpp:31-55`)
существовала **до** фичи `second_emission`. Git-история
(`git log -S'omp critical' на файле`): коммиты
«resolved 2 race conditions», «fix BC data races» — секция защищала записи в
буферы `BoundaryEmitter` и аккумуляторы `diag` для периодического переноса и
отражений.

Фича `second_emission` (этой ветки) **расширила содержимое секции**: теперь
для судьбы `Removed` внутри замка выполняется весь конвейер эмиссии —
RNG-сэмплирование, ламбертовская математика, запись вторичных в буферы.
Корректно, но каждая стенка сериализует N вторичных.

### Что реально мутируется под замком (по коду)

1. `emitter.current_species_buffer_` — периодика, bphi-отражение, отражение
   электронов (`boundary_condition_handler.cpp:32`, `bphi_condition.cpp:45`,
   `electron_reflection_condition.cpp:43`).
2. `emitter.species_buffers_` (map `<string, vector>`) — вторичная эмиссия
   (`second_emission_model.cpp:179`).
3. `particles.diag` (src-сорт) — `add_loss`/`add_reflected` из
   open/bphi/electron_reflection.
4. `product_species->diag` (другой сорт!) — `add_emitted` из
   `second_emission_model.cpp:180`.
5. `BphiCondition::Jz_` (2D-накопление; сейчас мёртвый код — `set_Bphi`
   нигде не вызывается).
6. `SecondaryEmissionModel::eng_` (LehmerEngine) — мутируется при сэмплировании.
7. (до исправлений этого ревью) `product_species_` — сырой указатель-кэш,
   убран.

Безымянные `#pragma omp critical` в `:31-34` и `:37-53` — один и тот же
глобальный замок OpenMP.

## 2. Подходы и оценка

| # | Подход | Корректность | Сложность | Перф | Вывод |
|---|--------|--------------|-----------|------|-------|
| 0 | «Это наша новая проблема?» | — | — | — | Нет, секция была; фича её разросла |
| 1 | Минимизировать область lock (математика наружу) | низкий риск | низкая | выигрыш мал | Косметика, проблему не решает |
| 2 | Per-thread буферы + per-thread RNG (мой исходный экспримент) | чистая, но ломает детерминизм | средняя-высокая | лучшая | Работает, но детерминизм от `OMP_NUM_THREADS` |
| 3 | **Двухфазный: параллельная классификация + последовательная эмиссия кандидатов после цикла (канонический порядок)** | чистая, детерминизму улучшает | средняя | эмиссия последовательна, но стенки редки | **Рекомендуется** |
| 4 | Внутренняя синхронизация `BoundaryEmitter` (mutex per species) | неполная (diag, RNG, Jz_ вне lock) | средняя | lock/unlock на вставку | Не выигрыш |
| 5 | Атомики для diag (compare_exchange) | гонка на `unordered_map::operator[]` в `SpeciesDiagStats`, буферы/RNG вне lock | — | false-sharing | Не рекомендован |
| 6 | Ничего не делать | корректно | — | проблема только при массовых стенках | Оправдано временно; для стенко-доминированных режимов — чинить |

### Мой (orchestrator) исходный выбор: вариант 2
Per-thread буферы эмиттера, per-thread RNG (seed = base + thread_num),
per-thread diag, merge после цикла. Достоинство: полное устранение замка.
Минусы: RNG per-thread со сломанным thread-count-детерминизмом, и per-thread
diag нужен для **обоих** сортов (src и продукта) — потому что `add_emitted`
пишет в diag сорта-продукта.

### Выбор @oracle: вариант 3 (двухфазный)
Параллельный цикл делает только **детерминированную классификацию**
судьбы (`contains`/`is_outside_face`) и копит в thread-local sink:
этот src-часть (`add_loss`/`add_reflected`/`emit_current_species`/`Jz_`) и
`EmissionCandidate {Particle, src, face}`. После цикла, в последовательной
фазе (за неявным барьером `parallel for`), диаг/буферы сливаются, кандидаты
сортируются в каноническом порядке (линейный индекс ячейки) и эмиссия
серийно вызывается через единственный `eng_`.

Плавает всего один дополнительный вид аккумулятора — потребуемый для
src-сорта, что гораздо проще, чем per-thread diag для `src+product`.

## 3. Сравнение

1. **Детерминизм.** Вариант 2: RNG per-thread — результат зависит от
   `OMP_NUM_THREADS` (раздражает в отладке). Вариант 3: порядок эмиссии
   канонический → **улучшает** детерминизм в сравенении со статус-кво
   (сейчас `eng_` потребляется в пор захват lock → недетерминирован).
2. **Перф.** Вариант 2 лучше (эмиссия самого масштаба параллельна).
   Вариант 3 сериализует эмиссию — стенки редки, так что дельта мала.
   Достаточно вылучает оба.
3. **Сложность.** Вариант 2: переделать `BoundaryEmitter` на поточные
   буферы и поточный diag (с ключом по сорту!). Вариант 3: `apply_to_particle`
   возвращает только судьбу (+candidate), поточные sink для src-сорта, и
   сливаем в хэндлере. Проще; не требует изменения интерфейса `diag`.
4. **Скоп.** Оба убирают `#pragma omp critical`; вариант 3 дополнительно
   позволяет `Jz_` (мёртвый код) просто отбросить в редукции.

**Этап принят:** выбор @oracle сильнее в трёх аспектах (детерминизм,
сложность, минимальный диаг-скоп), поэтому рекомендация — **вариант 3**.
Вариант 2 при нереалистической махе «бенчмарк любой ценой» может дать
дополнительный прирост, но это уже другой набор рисков.

## 4. Эскиз реструктуризации (вариант 3, по @oracle)

1. **Параллельная фаза** (без разделяемой записи):
   - `BoundaryCondition::apply_to_particle` возвращает `ParticleFateResult`
     только по детерминированным `contains`/`is_outside_face` (без
     побочных эффектов).
   - Побочные эффекты (потеря, отражение, Jz_) накопляются хэндлером в
     thread-local sink: `wrap_buf`/`reflect_buf`, локальный
     `SpeciesDiagStats`, `Jz_delta`, `vector<EmissionCandidate>`.
2. **Последовательная фаза** (после `#pragma omp parallel for`):
   - Слить буферы → `particles.add_particle`.
   - Суммировать diag → `particles.diag`.
   - Объединить кандидатов, отсортировать по каноническому
     `(ix,iy,iz,seq)`, вызвать `m.emit(...)` последовательно:
     `emit_to_species` + `add_emitted` безопасны однопоточно.
   - `flush_species` — без изменений.
3. `Jz_` (мёртвый) — отбросить или редуцировать.

**Заметка:** текущий код, детерминезательно, воспроизводится, но
это Scott-рандом по планировщику потоков. Устранять какой-либо обязательный
документ — её оставить в коде.

---

## Вердикт

- Критическая секция **не** нашederated от этой ветки; фича её расширила.
- **Лучший подход: №3, двухфазный классификатор + сортированная серийная
  эмиссия** — полное устранение троки и улучшение детерминизма.
- «Ничего не делать» оправдано только при низкой частоте стенок; целевые
  конфиги вторичной эмиссии — упираются в неё, поэтому чинить.
